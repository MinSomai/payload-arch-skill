# Payload Architecture Guide

> **Skill layering:** This skill covers *architectural decisions* — layering, file placement, dependency
> rules, and project-specific conventions. For deep PayloadCMS framework questions (collections, hooks,
> queries, access control, adapters, plugins), consult the **`payload` skill** alongside this one.
> The two skills are complementary: `payload` = what the framework can do; `payload-arch` = how this
> project is structured on top of it.
>
> **`src/payload-types.ts`** is auto-generated by Payload and is the single source of truth for all
> collection slugs, globals, job task names, and their TypeScript types. Read it whenever you need to
> know what collections or types exist — never guess or rely on memory.

This project follows a strict layered architecture. Every new file you create must fit into one of the
layers below. When you're unsure where something belongs, use this guide to decide.

## Layer Overview (outermost → innermost)

```
Route → Controller → Service → Store
```

**Dependency rule:** each layer may only call inward. A controller may call services and (through them)
stores, but never the reverse. A store must never import a service. A service must never import a
controller.

---

## Layer 1: Routes (`src/routes/*.routes.ts`)

Routes register Payload custom endpoints. They contain zero logic.

```ts
import SomeControllers from "@/controllers/some.controllers"
import { Endpoint } from "payload"

let controllers: SomeControllers | null = null
const getControllers = () => (controllers ??= new SomeControllers())

const someEndpoints: Endpoint[] = [
  {
    path: '/some/path',
    method: 'post',
    handler: (req) => getControllers().handleSomething(req),
  },
]

export default someEndpoints
```

**Instantiate controllers lazily — never at module top level.** A route file is pulled into the
Payload config graph (`@payload-config`), which is itself imported by many entry points. If the
controller is constructed eagerly (`const c = new SomeControllers()` at module scope), the *entire*
service/store tree behind it is constructed the moment the config is evaluated. When any of those
services participates in an import cycle back to the module currently being evaluated, you get a
temporal-dead-zone crash at build/startup:

```
Cannot access 'X' before initialization
```

The lazy getter (`??=`) defers construction until the first request actually hits the handler — by
then every module has finished initializing, so the cycle is harmless. Wrap each handler as
`(req) => getControllers().handleX(req)` so the controller isn't touched until invocation.

### Registration — where routes are wired up

Routes are **always registered inside a collection's `endpoints` array**, never as global endpoints
in `payload.config.ts`. The URL becomes `/api/<collection-slug>/<path>`.

**Simple collection** — spread the routes file directly in the collection config:

```ts
// src/collections/Courses/index.ts
import courseEndpoints from '@/routes/course.routes'

export const Courses: CollectionConfig = {
  slug: 'courses',
  // ...
  endpoints: [...courseEndpoints],
}
// → available at: /api/courses/some-path
```

**Collection with many endpoints** — use an aggregation file that combines imported routes with any
inline handlers, then spread that in the collection:

```ts
// src/collections/Evaluations/endpoints/index.ts
import evaluationEndpoints from '@/routes/evaluation.routes'
import { Endpoint } from 'payload'

const endpoints: Endpoint[] = [
  ...evaluationEndpoints,
  // additional inline entries only if they have no business logic
]

export default endpoints

// src/collections/Evaluations/index.ts
import endpoints from './endpoints'
export const Evaluations: CollectionConfig = {
  slug: 'evaluations',
  endpoints,
}
```

**Choosing which collection:** pick the collection that is semantically the subject of the endpoint.
Webhook integration endpoints live on the `webhooks` collection → `/api/webhooks/integrations/...`.

Rules:
- Export a single `Endpoint[]` array as default.
- Instantiate the controller **lazily** via a `getControllers()` getter — never `new` it at module
  top level (see the TDZ note above). Wrap handlers as `(req) => getControllers().handleX(req)`.
- No `if` statements, no request parsing, no imports of services or stores.
- Even inside `src/collections/<Domain>/endpoints/index.ts` — inline handlers must delegate to a
  controller, never contain business logic directly.
- File naming: `<domain>.routes.ts`.

## Layer 2: Controllers (`src/controllers/*.controllers.ts`)

Controllers parse the HTTP request, delegate entirely to service(s), and format the HTTP response.
Business logic does not belong here.

```ts
import SomeService from "@/services/some.service"
import { PayloadHandler, PayloadRequest } from "payload"

class SomeControllers {
  someService: SomeService

  constructor() {
    this.someService = new SomeService()
  }

  handleSomething: PayloadHandler = async (req: PayloadRequest) => {
    try {
      if (!req.json) return Response.json({ message: 'no payload' }, { status: 400 })
      const body = await req.json()

      const result = await this.someService.doSomething(body)
      return Response.json({ message: 'Success', data: result }, { status: 200 })
    } catch (e) {
      console.log({ e })
      return Response.json({ error: 'Something went wrong' }, { status: 400 })
    }
  }
}

export default SomeControllers
```

Rules:
- One class per file, exported as default.
- Handlers typed as `PayloadHandler = async (req: PayloadRequest) => Response`.
- Constructor instantiates all required services.
- May call multiple services, but never other controllers and never stores directly.
- Always wrap in try/catch and return `Response.json(...)` — never throw out of a handler.
- File naming: `<domain>.controllers.ts`.

## Layer 3: Services (`src/services/**/*.service.ts` or `*.services.ts`)

Services own all business logic. This is the most important layer — if you're unsure where code goes,
it's almost certainly a service.

```ts
import SomeStore from "@/store/some.store"
import CacheService from "@/services/cache.service"

class SomeService {
  someStore: SomeStore
  cacheService: CacheService

  constructor() {
    this.someStore = new SomeStore()
    this.cacheService = CacheService.getInstance()
  }

  doSomething = async (input: SomeInput) => {
    // business logic here
    const cached = await this.cacheService.get<SomeResult>(cacheKey)
    if (cached) return cached

    const record = await this.someStore.findById(input.id)
    // ... process record ...
    await this.cacheService.set(cacheKey, result, TTL)
    return result
  }
}

export default SomeService
```

### Third-party service wrappers

External APIs are wrapped as services in a subdirectory:

```
src/services/cloudConvert/cloudConvert.service.ts
src/services/moodle/moodleWebhook.service.ts
src/services/discord/discord.services.ts
```

The wrapper class is the only place that imports/calls the external SDK or HTTP client.

### Reusable cross-cutting services

| Service | Pattern | Purpose |
|---|---|---|
| `CacheService` | Singleton (`CacheService.getInstance()`) | Redis/in-memory caching |
| `AlertServices` | Static methods | Discord alert notifications |
| `AppSettingServices` | Instance | Payload global settings |
| `FeatureFlagService` | Instance | Feature flag reads |

When your service needs one of these, use the established pattern (singleton/static) rather than
constructing a new instance.

### Service lib helpers

Domain-specific pure helpers that a service uses internally live in `src/services/lib/`. These may
import from `src/lib` but not from other services or stores. Example:
`src/services/lib/evaluation.lib.ts`.

Rules:
- Class-based, exported as default.
- May call other services and stores — both are fine.
- Must never be called by a store.
- Must never import a controller.
- File naming: `<domain>.service.ts` (singleton pattern) or `<domain>.services.ts` (regular).

## Layer 4: Stores (`src/store/*.store.ts`)

Stores are the only place that talks to the Payload database via `getPayload()`. They contain pure
CRUD — no business logic, no external HTTP calls.

```ts
import { getPayload } from 'payload'
import configPromise from '@payload-config'

class SomeStore {
  async findById(id: string) {
    const payload = await getPayload({ config: configPromise })
    return payload.findByID({ collection: 'some-collection', id, depth: 0 })
  }

  async create(data: CreateSomeInput) {
    const payload = await getPayload({ config: configPromise })
    return payload.create({ collection: 'some-collection', data })
  }
}

export default SomeStore
```

Rules:
- Call `getPayload({ config: configPromise })` at the top of every method.
- `depth: 0` by default unless relationships must be populated — be explicit.
- No `if` blocks for business decisions. If there's a branch based on business rules, it belongs in
  a service that calls this store.
- Must never import a service or controller.
- File naming: `<domain>.store.ts`.

## Types (`src/types/`)

Domain-specific TypeScript interfaces and types that are shared across layers.

```ts
// src/types/evaluation.types.ts
export interface ISubmissionFile {
  task: { url: string; filename: string }
  submissions: { url: string; filename: string }[]
}
```

- Re-export everything from `src/types/index.ts` with `export * from './<domain>.types'`.
- File naming: `<domain>.types.ts`.
- Types used only within a single service or component can stay local to that file — only extract to `src/types/` when two or more files need the same type.
- Payload-generated types (from `payload-types.ts`) are imported from `@/payload-types`, not from `src/types/`.

## Utils (`src/utils/`)

Domain-specific pure helper functions that work with domain types but have no DB or HTTP dependency.

```ts
// src/utils/evaluation.utils.ts
import { Evaluation } from '@/payload-types'

export const getSubmissionFiles = (evaluation: Evaluation) => { ... }
```

- Re-export from `src/utils/index.ts`.
- File naming: `<domain>.utils.ts`.
- **Distinction from `src/lib/`**: `lib/` is for generic, domain-agnostic helpers (e.g. `cn()`, parsers, the SDK client). `utils/` is for helpers that are specific to this app's domain model but still pure. When in doubt: if it imports from `@/payload-types` or `@/types`, it belongs in `utils/`; if it's generic enough to copy to any project, it belongs in `lib/`.

## Access Control (`src/access/`)

Payload access control functions used in collection/field/global configs.

```ts
// src/access/adminOnly.ts
import { Access } from 'payload'
import checkRole from './checkRole'
import { ROLES } from './roles'

const adminOnly: Access = ({ req: { user } }) => {
  if (user?.collection !== 'users') return false
  return checkRole([ROLES.ADMIN], user)
}

export default adminOnly
```

- `src/access/roles.ts` — the canonical list of role strings (`ROLES.ADMIN`, `ROLES.USER`, etc.). Always import roles from here, never hardcode strings.
- `src/access/checkRole.ts` — the shared role-checking helper.
- One file per access rule, imported directly into collection configs.

## Constants (`src/const/`)

- Each domain gets its own file: `src/const/<domain>.const.ts`
- All are re-exported from `src/const/index.ts`
- Use `Object.freeze()` for objects so values can't be mutated at runtime
- Named exports only — no default exports

```ts
// src/const/cache.const.ts
const CACHE_KEYS = Object.freeze({
  FEATURE_FLAGS: 'feature-flags',
  USER_OPT_IN_PREFIX: 'user-opt-in-prefix',
})

const DEFAULT_KEY_EXPIRATION = 86400000 // 24 hours

export { CACHE_KEYS, DEFAULT_KEY_EXPIRATION }
```

Then add `export * from './cache.const'` to `src/const/index.ts`.

## Environment Config (`src/config/config.ts`)

All `process.env.*` reads happen exactly here and nowhere else.

```ts
const config = () => {
  const config = {
    NODE_ENV: process.env.NODE_ENV || 'development',
    SOME_API_KEY: process.env.SOME_API_KEY || '',
    ENABLE_FEATURE: process.env.ENABLE_FEATURE === 'true',
  }
  return config
}

export type SYSTEM_CONFIG = ReturnType<typeof config>
export default config
```

Services call `config()` to get the typed object. Never read `process.env` directly in services,
stores, or controllers.

## Lib (`src/lib/`)

Pure TypeScript utilities with zero dependency on services, stores, or external APIs.

```ts
// src/lib/utils.ts
export function slugify(text: string): string {
  return text.toLowerCase().replace(/\s+/g, '-')
}
```

Rules:
- No imports from `@/services`, `@/store`, or any external HTTP/DB library.
- Functions only — no classes needed.
- Shared across all layers; any layer may import from `src/lib`.
- File naming: `<purpose>.ts` or `<domain>.<purpose>.ts`.

## Jobs (`src/jobs/`)

Background work is split into two files per domain:

- `src/jobs/<domain>.jobs.ts` — task definitions (`TaskConfig` objects with slug, inputSchema, outputSchema, handler)
- `src/jobs/<domain>.workflows.ts` — workflow definitions that chain tasks

Task handler functions live either in `src/runners/` (legacy) or in `src/jobs/tasks/` (preferred for
new code). Keep tasks and workflows separated.

```ts
// src/jobs/evaluation.jobs.ts
import { TaskConfig } from 'payload'
import { handleEvaluationTask } from '@/jobs/tasks/evaluation.task'

const startEvaluationJob = {
  slug: 'startEvaluationTask',
  inputSchema: [
    { name: 'evaluationId', type: 'text', required: true },
  ],
  outputSchema: [
    { name: 'evaluationId', type: 'text', required: true },
  ],
  handler: handleEvaluationTask,
} as TaskConfig<'startEvaluationTask'>

export { startEvaluationJob }
```

Task handlers may import services to do their work — jobs are consumers of the service layer.

## Server vs Client Data Boundary

This is the most important architectural decision in the Next.js layer. The rule:

| What | Where | How |
|---|---|---|
| Auth check + redirect | Server page | `payload.auth({ headers })` → redirect if no user |
| Primary entity for the page | Server page | `payload.findByID(...)` → passed as prop |
| Secondary/related data | Client component | `useSWR` + `payloadClientSDK` |
| Live-updating data (job status) | Client component | `useSWR` with `refreshInterval` |
| Mutations (create/update/delete) | Client component | `payloadClientSDK` imperatively |

### The page → component handoff pattern

Every page in this project follows the same shape:

```tsx
// app/dash/courses/[courseId]/page.tsx  ← Server Component
import { getPayload } from 'payload'
import configPromise from '@payload-config'
import { headers as getHeaders } from 'next/headers'
import { redirect } from 'next/navigation'
import CourseDetail from '@/components/dash/CourseDetail'

export default async function CoursePage({ params }: { params: Promise<{ courseId: string }> }) {
  const headers = await getHeaders()
  const payload = await getPayload({ config: configPromise })
  const { user } = await payload.auth({ headers })

  if (!user) redirect('/login')

  const { courseId } = await params
  const course = await payload.findByID({ collection: 'courses', id: courseId, depth: 0 })

  if (!course) return <div>Not found</div>

  return <CourseDetail user={user} course={course} />   // hand off to client
}
```

```tsx
// components/dash/CourseDetail.tsx  ← Client Component
"use client"
export default function CourseDetail({ user, course }: Props) {
  // course is already loaded — no SWR needed for it
  // SWR handles everything secondary/dynamic
  const { data: assignments = [] } = useSWR(
    getCourseAssignmentsKey(course.id),
    fetchAssignments,
  )
  ...
}
```

### Decision guide

**Fetch in the server page when:**
- It's the main entity the URL is about (the course, the evaluation, the group)
- The page should 404 or redirect if it doesn't exist
- The data never changes while the user is on the page

**Fetch with SWR in the client component when:**
- It's related data that's secondary to the page's main entity
- It can change while the user is on the page (submissions, status, counts)
- It depends on user interaction (search, pagination, filters)
- You need to mutate it after a write

**Never do:**
- `getPayload()` in a client component — it's a server-only API
- `payloadClientSDK` in a server component or page — it's for client use only
- Fetch the same data in both the server page AND via SWR — pick one

## Frontend API Client (`payloadClientSDK`)

All client-side Payload API calls go through `payloadClientSDK`, imported from `@/lib/payload.client`.
It is a typed instance of `PayloadSDK` from `@payloadcms/sdk`, configured with the app's generated
`Config` type and `credentials: 'include'` so session cookies are sent automatically.

```ts
import { payloadClientSDK } from '@/lib/payload.client'
```

Only use it in client components (`"use client"`). On the server (stores, services, Server Components,
route handlers), always use `getPayload()` from `payload` instead.

### Common operations

```ts
// Read list — supports where, depth, limit, page, sort, select, pagination
const result = await payloadClientSDK.find({
  collection: 'courses',
  depth: 0,
  limit: 10,
  page: 1,
  sort: '-createdAt',
  where: { status: { equals: 'active' } },
  select: { name: true, code: true },
})
// result.docs, result.totalDocs, result.totalPages

// Read single record
const course = await payloadClientSDK.findByID({
  collection: 'courses',
  id: courseId,
  depth: 1,
})

// Count
const { totalDocs } = await payloadClientSDK.count({
  collection: 'evaluations',
  where: { status: { not_equals: 'COMPLETED' } },
})

// Create (with optional file upload)
const created = await payloadClientSDK.create({
  collection: 'submission-files',
  data: { user: userId },
  file: fileObject,        // optional — for upload collections
})

// Update
const updated = await payloadClientSDK.update({
  collection: 'groups',
  id: groupId,
  data: { submissions: [...ids] },
  depth: 0,
})

// Delete
await payloadClientSDK.delete({
  collection: 'groups',
  id: groupId,
})

// Custom endpoint (e.g. a Payload custom route)
const res = await payloadClientSDK.request({
  method: 'POST',
  path: '/courses/check-unique-code',
  json: { code: courseCode },
})
const data = await res.json()
```

### Rules

- **Client components only** — never import `payloadClientSDK` in a file without `"use client"`.
- **Never use raw `fetch()`** for Payload API calls in components — always go through `payloadClientSDK`.
- **`depth: 0` by default** — only increase when you actually need the populated relationship in the UI.
- **`pagination: false`** when you need all records and pagination would truncate results.
- **`select`** to trim response payloads — only request fields you render.
- Use `payloadClientSDK.request()` for custom endpoints registered in the routes layer.

## Frontend Data Fetching with SWR (`src/components/`)

All client-side data fetching uses [SWR](https://swr.vercel.app/). Never use `useEffect` + `useState`
to fetch data — that pattern causes double-renders, no deduplication, and no cache sharing.

### Full pattern

```tsx
// 1. Export a key factory — the tuple format lets SWR deduplicate across components
export const getCourseAssignmentsKey = (courseId: string) =>
  ['course-assignments', courseId] as const;

// 2. Define the fetcher outside the component (no closure over props)
//    Destructure the key tuple — first element is the cache namespace, rest is params
const fetchAssignments = async ([, courseId]: [string, string]): Promise<Assignment[]> => {
  const result = await payloadClientSDK.find({
    collection: 'assignments',
    depth: 0,
    where: { course: { equals: courseId } },
  });
  return result.docs;
};

// 3. Use in component — always provide a default value
const { data: assignments = [], isLoading } = useSWR(
  getCourseAssignmentsKey(course.id),
  fetchAssignments,
);
```

### Key rules

- **Always export the key factory** — other components can call `mutate(getCourseAssignmentsKey(id))`
  to invalidate the cache after a write.
- **Always use `payloadClientSDK`** — never raw `fetch()` or axios in components.
- **Simple string keys** are fine when there are no params: `useSWR('welcome-banner-courses', fetchCourses)`.
- **Fetcher needs a variable not in the key** (e.g. a full object, not just an id)? Use a closure:
  ```tsx
  useSWR(getGroupSubmissionsKey(group.id), () => fetchSubmissions(group))
  ```
- **Always provide a default**: `data: items = []` or `data: result = null` — never let data be `undefined` in JSX.

### Optimistic / manual mutation

After a write that should update a cached list, use `mutate` from the `useSWR` call instead of
re-fetching everything:

```tsx
const { data: submissions = [], mutate: mutateSubmissions } = useSWR(
  getGroupSubmissionsKey(group.id),
  () => fetchSubmissions(group),
);

// After uploading new files, append to cache without re-fetching
mutateSubmissions(
  current => [...(current ?? []), ...newSubmissions],
  { revalidate: false },
);
```

### Polling for live status

When a record has a status that changes server-side (e.g. an evaluation moving from `PENDING` →
`RUNNING` → `COMPLETED`), use SWR's `refreshInterval` to poll until done. Stop polling once the
terminal state is reached by returning `null` from the key function — SWR will not fetch when the
key is `null`.

```tsx
const TERMINAL_STATUSES = ['COMPLETED', 'CANCELLED', 'TERMINATED', 'ERROR']

const isTerminal = (status?: string) => TERMINAL_STATUSES.includes(status ?? '')

// Key returns null once done → SWR stops fetching automatically
const { data: evaluation } = useSWR(
  isTerminal(evaluation?.status) ? null : getEvaluationStatusKey(evaluationId),
  fetchEvaluationStatus,
  { refreshInterval: 3000 },
)
```

Don't use `setInterval` or `useEffect` for polling — SWR handles deduplication, revalidation on
focus, and cleanup automatically.

### What NOT to do

```tsx
// ❌ Never use useEffect + setState for data fetching
useEffect(() => {
  payloadClientSDK.find({ collection: 'courses' }).then(res => setCourses(res.docs));
}, []);

// ❌ Don't define the fetcher inside the component (recreated every render)
const MyComp = ({ courseId }) => {
  const fetcher = () => payloadClientSDK.find(...); // bad
  const { data } = useSWR(key, fetcher);
};

// ✅ Define fetcher at module level
const fetchCourses = async ([, courseId]: [string, string]) => { ... };
const MyComp = ({ courseId }) => {
  const { data } = useSWR(getCourseAssignmentsKey(courseId), fetchCourses);
};
```

## Custom Admin Components

PayloadCMS lets you inject React components into the admin panel — custom field inputs, UI fields,
row labels, cells, view overrides, etc. These are **not** the dashboard components covered above;
they render *inside* the Payload admin UI and talk to the form through Payload's own hooks, not SWR.

### Registration

Components are referenced from a collection/field config by **import path string** (Payload builds a
component map at build time — you never import the component into the config directly):

```ts
// src/collections/Evaluations/index.ts
{
  name: 'prefillData',
  type: 'ui',                       // a UI field renders a component but stores nothing
  admin: {
    components: {
      Field: '@/components/admin/PrefillData',   // path string, not an import
    },
  },
}
```

### Client component pattern

Any component that uses Payload UI hooks or React state must be a client component. Type it with the
matching Payload type (`UIFieldClientComponent`, `TextFieldClientComponent`, `FieldClientComponent`,
etc.) so the injected props are correct.

```tsx
'use client'

import { useEffect, useRef } from 'react'
import { useDocumentInfo, useField, useFormInitializing } from '@payloadcms/ui'
import { useSearchParams } from 'next/navigation'
import type { UIFieldClientComponent } from 'payload'

const PrefillData: UIFieldClientComponent = () => {
  const searchParams = useSearchParams()
  const { isEditing } = useDocumentInfo()
  const { setValue: setCourse } = useField({ path: 'course' })
  const { value: nameValue, setValue: setName } = useField<string>({ path: 'name' })

  const isFormInitializing = useFormInitializing()
  const hasPrefilled = useRef(false)

  useEffect(() => {
    // ⛔ Bail until the form has finished initializing — see note below.
    if (isEditing || isFormInitializing || hasPrefilled.current) return

    const course = searchParams.get('course')
    if (!course) return

    hasPrefilled.current = true        // run-once guard
    setCourse(course)                  // conditionally-shown fields: set in dependency order

    // Default values set during initialization are now safe to read/modify.
    if (nameValue && !nameValue.endsWith('__MANUAL')) {
      setName(`${nameValue}__MANUAL`)
    }
  }, [isEditing, isFormInitializing, searchParams, setCourse, nameValue, setName])

  return null   // side-effect-only UI fields render nothing
}

export default PrefillData
```

### Key hooks

| Hook | Returns | Use for |
|---|---|---|
| `useField({ path })` | `{ value, setValue }` | read/write one field's value in the live form |
| `useFormInitializing()` | `boolean` | **gate all form reads/writes until `false`** (see below) |
| `useDocumentInfo()` | `{ isEditing, id, ... }` | distinguish create vs edit, get the doc id |
| `useForm()` | form context (`fields`, `dispatchFields`, ...) | lower-level, multi-field operations |

### `useFormInitializing()` — the critical one

**Always gate field reads and writes on `useFormInitializing()`.** While the form is initializing,
Payload is still applying `defaultValue`s and hydrating existing data. If you `setValue` during that
window your write is **clobbered** by the initialization pass, and if you *read* a value you get a
stale/empty one. Waiting until `isFormInitializing === false` guarantees:

- default values (like the auto-generated `name`) are already present, so you can safely read and
  amend them, and
- your `setValue` calls survive instead of being overwritten.

Pair it with a `useRef` run-once guard (`hasPrefilled`) so the effect fires exactly once after
initialization, not on every dependency change.

### Rules

- **`'use client'`** on every component that uses these hooks — they are client-only.
- **Register by path string**, never by importing the component into the config.
- **Type with the Payload `*ClientComponent` / `*ServerComponent` type** for correct injected props.
- **Gate every form read/write on `!isFormInitializing`** — the single most common source of
  "my default disappeared" / "my value didn't stick" bugs.
- **Use `useField`/`useForm` to touch form state** — never reach for SWR or `payloadClientSDK` to
  read the record being edited; it's already in the form.
- **Set conditionally-rendered fields in dependency order** (parent before child).
- **File placement:** `src/components/admin/<Name>.tsx` (kept separate from dashboard components).

## File Placement Cheat Sheet

| What you're writing | Where it goes |
|---|---|
| HTTP endpoint registration | `src/routes/<domain>.routes.ts` |
| Endpoint aggregation (complex collections) | `src/collections/<Domain>/endpoints/index.ts` |
| Request parsing + response formatting | `src/controllers/<domain>.controllers.ts` |
| Business logic | `src/services/<domain>.service.ts` |
| Third-party API wrapper | `src/services/<vendor>/<vendor>.service.ts` |
| Database queries (Payload CRUD) | `src/store/<domain>.store.ts` |
| Reusable pure helpers | `src/lib/<purpose>.ts` |
| App constants / magic strings | `src/const/<domain>.const.ts` + re-export in `src/const/index.ts` |
| Environment variables | `src/config/config.ts` |
| Background task definition | `src/jobs/<domain>.jobs.ts` |
| Background workflow definition | `src/jobs/<domain>.workflows.ts` |
| Task handler function | `src/jobs/tasks/<domain>.task.ts` (or `src/runners/` for legacy) |
| Domain-specific service utilities | `src/services/lib/<purpose>.lib.ts` |
| Client-side data fetching | `useSWR` in the component file, key factory exported |
| Custom admin panel component (field/UI/cell) | `src/components/admin/<Name>.tsx`, registered by path string |
| Domain-specific TypeScript types | `src/types/<domain>.types.ts` + re-export in `src/types/index.ts` |
| Domain-specific pure utilities | `src/utils/<domain>.utils.ts` + re-export in `src/utils/index.ts` |
| Payload access control functions | `src/access/<name>.ts` |

## Common Mistakes to Avoid

- **Instantiating a controller at module top level in a route file** — `const c = new SomeControllers()`
  eagerly builds the whole service/store tree when the Payload config is evaluated, and triggers a
  temporal-dead-zone crash (`Cannot access 'X' before initialization`) whenever a service in that tree
  imports back into a module still initializing. Use the lazy `getControllers()` getter instead.
- **Reading `process.env` outside `config.ts`** — always go through `config()`.
- **Putting logic in a controller** — if you write an `if` that isn't about the HTTP request shape,
  it belongs in a service.
- **Calling `getPayload()` in a service** — that's what stores are for. Create a store and call it
  from the service. (Exception: services that are tightly coupled to Payload internals like
  `AlertServices` may call `getPayload()` directly for logging, but prefer stores for data access.)
- **Importing a service from a store** — inward-only rule violation.
- **Hardcoding strings that are used in multiple places** — put them in `src/const/`.
- **Writing a helper with a DB/HTTP dependency and putting it in `src/lib/`** — `lib` is pure code
  only. Put impure helpers in `src/services/lib/` instead.
- **Creating a new `CacheService` instance** — it's a singleton, always use `CacheService.getInstance()`.
- **Using `useEffect` + `useState` to fetch data** — always use `useSWR` instead.
- **Defining the SWR fetcher inside the component** — define it at module level so it isn't recreated every render.
- **Not exporting the key factory** — always export it so other components can invalidate the cache via `mutate`.
- **`getPayload()` in a client component** — server-only, will break at runtime.
- **`payloadClientSDK` in a server page** — client-only, use `getPayload()` in pages instead.
- **Fetching the same data in both the page and via SWR** — pick one. Page → seed data for the primary entity. SWR → everything secondary and dynamic.
- **Reading or writing form fields before `useFormInitializing()` is `false`** in a custom admin component — your `setValue` gets clobbered by initialization and reads return stale/empty values. Always gate on `!isFormInitializing` and use a `useRef` run-once guard.

## CLAUDE.md Template for New Projects

When starting a new PayloadCMS project that follows this architecture, create a `CLAUDE.md` in the
project root. Keep it short — the `payload-arch` skill handles all the rules. The CLAUDE.md should
only capture what's unique to that project.

```markdown
# <Project Name>

<One sentence: what this app does.>

## Stack
- PayloadCMS + Next.js App Router + TypeScript
- Architecture: follows `payload-arch` skill conventions
- DB: <MongoDB / PostgreSQL>
- Cache: <Redis / in-memory>

## Collections, Globals & Jobs
See `src/payload-types.ts` — the `Config` interface is the single source of truth for all collections,
globals, jobs/tasks, and workflows with their full TypeScript types. Do not duplicate this list here.

## Key env vars
- `<VAR_NAME>` — <what it's for>
<!-- only the non-obvious ones; standard ones like DATABASE_URL don't need explanation -->

## Project-specific conventions
<!-- Only note things that DEVIATE from or EXTEND the payload-arch skill defaults. -->
<!-- If everything follows the skill, this section can be omitted. -->
- <e.g. "All webhook events are stored before processing — never process without persisting first">
- <e.g. "The `runners/` directory is legacy; new tasks go in `jobs/tasks/`">
```

**Rules for writing a good CLAUDE.md:**
- Do NOT repeat anything already in the `payload-arch` or `payload` skills.
- One sentence per collection/global is enough — Claude can read the code for details.
- Only list env vars that aren't obvious from their name.
- The "project-specific conventions" section is the most valuable — it's where intentional deviations live.
